## 2. The state machine

Everything in this group is `Core/Dictation/DictationOrchestrator.cs`, unit-tested in
`Core.Tests/Dictation/` over fakes for `IGlobalHotkeyService`, `IAudioCapture`, `IAudioEncoder`,
`ITranscriptionProvider` and `ITextOutput`. No task here needs a microphone, a network, a keyboard or
a clipboard, and no test waits a real 50 ms, 200 ms or 120 s — the internal constructor from 1.2
supplies all four.

- [x] 2.1 Subscribe to `IGlobalHotkeyService.Pressed` and `Released` **in the constructor**, and make both handlers claim a state transition under a single `Lock` and return without awaiting anything. Verify: unit test with a fake capture whose `Start()` blocks, asserting the handler returned while the pipeline is still running; and a second asserting that a `Released` raised immediately after `Pressed` is still acted on, which is the regression test for blocking change 6's dispatch loop.
- [x] 2.2 Implement hold-to-record: `Pressed` starts a recording, `Released` stops it and runs the pipeline. Verify: unit test over the happy path asserting the call order `IAudioCapture.Start` → `StopAsync` → `IAudioEncoder.Encode` → `ITranscriptionProvider.TranscribeAsync` → `ITextOutput.DeliverAsync`, each exactly once.
- [x] 2.3 Implement toggle mode: `Pressed` starts when idle and stops when recording, `Released` does nothing at all. Verify: unit tests for the first press starting, a release changing nothing, and a later press stopping and transcribing.
- [x] 2.4 Implement the 200 ms debounce, in toggle mode only, recording the press timestamp before deciding what the press means so it debounces in both directions. Verify: unit tests over the injected clock for a second press inside the window being ignored, one outside it being acted on, and hold-to-record being unaffected by it.
- [x] 2.5 Implement the 50 ms minimum: a recording shorter than that stops the capture, discards the samples, publishes `Idle` and reports nothing. Verify: unit tests asserting no transcription was attempted, that `Transcribing` was never published, and that nothing was described as a failure.
- [x] 2.6 Implement the empty-capture fault: a recording at or over the minimum duration that returns no samples raises an `AudioException` naming that no audio was recorded, rather than being discarded. Verify: unit tests for the two halves of the diagnosis — empty samples over the minimum describing a recording error, empty samples under it discarding silently.
- [x] 2.7 Implement the two concurrency guards: a press while recording returns silently, and a press while transcribing starts nothing and reports that a transcription is in progress. Verify: unit tests asserting no second capture was started in either case, and that only the transcribing case produced a message.
- [x] 2.8 Implement the max-duration watchdog as a `CancellationTokenSource` plus `Task.Delay`, armed from `AppSettings.MaxRecordingDurationSecs` when the recording starts and cancelled when it ends by any other route. Verify: unit tests with a short injected maximum asserting that it fires, stops and *transcribes* rather than discarding; that a normal stop cancels it; and that the token source is disposed so a dictation leaves nothing running.
- [x] 2.9 Make the transition out of `Recording` an atomic claim, so that the release edge, a toggle press and the watchdog cannot both run the pipeline over one capture. Verify: unit test driving the watchdog and a release concurrently, asserting `StopAsync` and `TranscribeAsync` were each called exactly once.
- [x] 2.10 Publish `StateChanged` at the three points the design fixes: `Recording` when the capture starts, `Transcribing` when the stop is *claimed* rather than when `StopAsync` returns, and `Idle` from the `finally`. Verify: unit tests recording the sequence for a successful dictation (`Recording`, `Transcribing`, `Idle`), for a discarded short press (`Recording`, `Idle` — no `Transcribing`), and for a dictation whose pipeline threw (still ending at `Idle`).

## 3. The pipeline

- [x] 3.1 Run the pipeline on a pooled task: `StopAsync`, then `Encode(samples, IAudioCapture.SampleRate, settings.AudioFormat)`, then `TranscribeAsync`, then `DeliverAsync` — reading the audio format and the maximum duration from `SettingsStore.Current` per dictation with no caching and no change subscription, following `GeminiProviderPool`'s precedent. Verify: unit test asserting the encoder received the constant from 1.1 and the format currently in settings, and a second asserting a settings change between two dictations is picked up by the second.
- [x] 3.2 Resolve the active preset's system prompt from `SettingsStore.Current` at transcription time and pass it to `TranscribeAsync`. Verify: unit tests asserting the active preset's prompt is what arrives, and that changing the active preset between dictations changes it — relying on `SettingsStore.Load` having already repaired an unresolvable `ActivePresetId`, which is why no fallback prompt is needed here.
- [x] 3.3 Implement the two cancellation tokens: a shutdown `CancellationTokenSource` for the orchestrator's lifetime, and a linked source adding the 120 s budget that wraps `TranscribeAsync` **only**; `DeliverAsync` receives the shutdown token alone. Verify: unit tests asserting that a transcription exceeding the injected budget is cancelled, that a delivery in progress is *not* cancelled when the budget expires, and that a completed transcription is unaffected by it.
- [x] 3.4 Treat `TextOutputOutcome.ClipboardOnly` as a successful dictation needing a word to the user, not a failure. Do **not** repeat `TextOutput`'s diagnosis — it already logs why the paste did not happen on both degraded paths — but do record the user-facing manual-paste message once, which the spec requires the user to be told and which change 11 will say out loud. Verify: unit test with a fake `ITextOutput` returning `ClipboardOnly` asserting nothing was described as a failure, the state still returned to `Idle`, and the manual-paste message was recorded exactly once.
- [x] 3.5 Wrap the whole pipeline task in `try`/`catch`/`finally`, with the `finally` resetting the state and publishing `Idle`, so that an exception nobody anticipated cannot be swallowed as an unobserved task exception and leave the hotkey answering "Transcription In Progress" for ever. Verify: unit tests throwing from each of the four stages in turn, asserting the state returns to `Idle` every time and that the next hotkey press starts a new recording.

## 5. Lifecycle and composition

- [x] 5.1 Implement `IHostedService`: `StartAsync` does nothing beyond what the constructor already did, and `StopAsync` cancels the shutdown token **and awaits the pipeline task**, stopping and discarding a recording in progress. Verify: unit tests for shutdown while recording (capture stopped, no transcription started), while transcribing (abandoned promptly rather than waiting out the budget), and while delivering — the last asserting `StopAsync` did not return until `DeliverAsync` had completed, which is the test that protects the user's clipboard from being destroyed by an exit inside the restore window.
- [x] 5.2 Add `AddDictationPipeline` in `Core/Dictation/DictationServiceCollectionExtensions.cs`, registering the orchestrator once and resolving it as both the singleton and `IHostedService` in `AddGlobalHotkey`'s shape, and call it from `Program.cs` after the four capabilities it consumes. Verify: registration test in the shape of `TranscriptionRegistrationTests` building a host with `ValidateOnBuild` on and resolving the orchestrator, plus a test asserting the same instance is returned for both roles.
- [x] 5.3 Enforce the logging rules: the transcript is never written at any level, and this component logs no hotkey edge, because change 6's dispatch loop already logs every edge at `Information` and a second line would double the most common lines in the file. Verify: unit test wiring change 3's `RecordingSink` at `Verbose` through a full dictation, asserting no emitted message or property contains the transcript, that the recording's duration and sample count are present, and that no message mentions a key — the same shape as change 6's task 3.10 and change 7's task 2.9. The transcript's character count is deliberately **not** logged here: `TextOutput` already logs `Delivered {CharacterCount} characters: {Outcome}`, and repeating it is the duplication this task exists to avoid.
