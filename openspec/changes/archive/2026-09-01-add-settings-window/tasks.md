## 2. The edit model

Everything in this group is `App/Settings/SettingsEditor.cs` plus its tests in
`App.Tests/Settings/`. None of it needs Avalonia: the delay is injected, the store is constructed
over a temp path, and no test waits 400 ms of real time.

- [x] 2.1 Write `SettingsEditor` with `void Edit(Action<AppSettings> edit)` and `Task FlushAsync()`, holding a pending clone under a `Lock`, taking `SettingsStore`, `ILogger<SettingsEditor>` and — through an `internal` constructor in `GlobalHotkeyService`'s and `DictationOrchestrator`'s shape — an injected `Func<TimeSpan, CancellationToken, Task>` delay defaulting to `Task.Delay`. `CommitDelay` is a `const` of 400 ms and deliberately **not** a setting. Verify: unit tests asserting the first `Edit` clones from `Current` and does not save, that the save lands after the injected delay completes, and that `SettingsStore.Save` was called exactly once.
- [x] 2.2 Make the delay restart on each `Edit` so continuous typing coalesces, and make the pending clone accumulate edits within one quiet window. Verify: unit tests asserting five `Edit` calls inside one window produce **one** `Save` carrying all five changes, and that two edits separated by a completed delay produce two saves.
- [x] 2.3 Take the clone **at the start of each quiet window**, never once per editor lifetime, and null the pending draft after a commit. This is the rule that stops a stale draft reverting a preset written through `SettingsStore.SavePreset`. Verify: unit test that edits a field, flushes, then calls `store.SavePreset` with a new preset, then edits another field and flushes — asserting the new preset is still present afterwards. This test is the regression guard for the whole clone decision; name it so.
- [x] 2.4 Implement `FlushAsync`: commit immediately if a draft is pending, complete immediately if not, and be safe to call twice. Verify: unit tests for a pending draft being written before `FlushAsync` returns, for a no-op flush, and for two concurrent flushes producing one save.
- [x] 2.5 Establish the **edit-by-id invariant** that the clone forces, and document it on `SettingsEditor.Edit` itself so it is read by anyone writing a delegate: an edit locates its target inside the `AppSettings` it is handed, by `Id`, and never through a reference captured from an earlier `Current`. `Save` assigns `Current = draft`, so the graph is replaced on every commit and a captured `ProviderConfig` or `Preset` belongs to a graph nothing will save — the edit vanishes with no exception. Use `FirstOrDefault` and return when the id is gone, never `First`: a removal and a keystroke can land in the same quiet window, and a `First` here throws on the pooled commit thread as an unobserved task exception. Verify: unit tests asserting an edit made **after** a completed commit still reaches the next draft — the test that fails if a delegate captured a reference — and that an edit naming an id removed earlier in the same window is a no-op rather than a throw.
- [x] 2.6 Log at `Debug` what was committed as a **count of changed settings and nothing more** — no field names, no values, and above all no provider entries. `CLAUDE.md` forbids logging API key values and this type holds the object that carries them. Verify: unit test wiring change 3's `RecordingSink` at `Verbose` through an edit that sets an API key, asserting no emitted message or property contains the key.

## Not in this change

Recorded so they are not mistaken for oversights, each with its owner:

- **Autostart and notifications.** The General tab persists `StartWithSystem` and
  `ShowTrayNotifications`; nothing acts on either. Change 11, which is next. `design.md` records why
  the rows ship inert rather than waiting.
- **Rendering `HotkeyAvailability.Failed` as a notification.** This change disables the recorder and
  shows a banner *inside the window*, which is what stops a hang. Telling a user whose hotkey is dead
  and who never opens the window is change 11's, as change 9 recorded.
- **A settings-file watcher.** `SettingsStore` is cache-authoritative and documents that a hand edit
  made while the application runs is lost at the next save. Unchanged here; the store's own remarks
  already name the debounced watcher as the upgrade path.
- **A dark theme.** Non-goal. The window pins `ThemeVariant.Light` rather than leaving `FluentTheme`
  to follow the OS, so the non-goal is enforced instead of assumed.
- **Rendering the settings window's layout in tests.** Headless tests prove a view loads and binds,
  not that it is legible or well proportioned. That stays manual, in 6.1 and 6.2.
- **A provider type other than Gemini.** The reference's Providers tab has a Gemini/OpenAI dropdown;
  `ProviderConfig` here has no `providerType` field and OpenAI is an out-of-scope standing decision.
