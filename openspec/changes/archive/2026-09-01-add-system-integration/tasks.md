## 2. The toast

Everything here is `src/Pisum.Whisper.App/Notifications/`. There is deliberately **no type in
`Core`** for the presentation, following changes 9 and 10 — the tray icon and the settings window are
both App-only — and `design.md` records why the seam sits at `INotificationPresenter` instead.

- [x] 2.1 Add `ToastWindow.axaml` and its code-behind, following the settings window's axaml-plus-code-behind layout rather than the spike's code-only construction. `ShowActivated = false`, `Topmost = true`, `ShowInTaskbar = false`, `WindowDecorations = WindowDecorations.None`, `CanResize = false`, 360 x 96 logical. **`SystemDecorations` is obsolete in 12.1** in favour of `WindowDecorations`; using the old name is a warning and therefore a build failure. Place from `Screens.Primary`'s `WorkingArea` and `Scaling`, 16 logical from both edges: bottom-right stacking upward on Windows, **top-right stacking downward on macOS**, because that is where each platform's notifications live. `Position` is physical pixels while `Width` and `Height` are not, which is the whole reason `Scaling` is read. Fixed appearance — explicit brushes, a dark card with light text, no `FluentTheme` dependency — so the dark-theme non-goal is sidestepped rather than reopened. Verify: `[AvaloniaFact]` in `App.Tests/Notifications` asserting the window shows, that its computed position for slot 0 and slot 1 both fall inside a stubbed working area, and that the two rectangles do not intersect; `dotnet build Pisum.Whisper.slnx` at 0 warnings. **And assert `ShowActivated` is false, `Topmost` true and `ShowInTaskbar` false on the constructed window.** Headless Avalonia has no meaningful notion of focus, so nothing here can test the *behaviour* — but `ShowActivated` is the mechanism, S7 measured that Avalonia honours it, and without this assertion deleting that one line fails no test at all. The spec's *A notification never takes focus* is the requirement that breaks the product rather than annoying the user, and it is otherwise verified only by hand in 7.1.
- [x] 2.2 Add `ToastPresenter : INotificationPresenter`. `Present` posts to `Dispatcher.UIThread` and **returns immediately** — it may not wait for the window, and an implementation that does is wrong, because two call sites run on the hotkey dispatch loop where the next item may be the release edge ending a recording. Own the live list, assign slots, cap at **three** concurrent with a fourth closing the oldest, and dismiss each after 6 s with a `DispatcherTimer` whose dwell is **injected as a `TimeSpan`** so no test waits six seconds — the precedent is `SettingsEditor`'s injected debounce and `GeminiProvider`'s injected backoff. Verify: `[AvaloniaFact]`s covering the cap, the dismissal, and that `Present` returns before the window exists; plus a test that calls `Present` from a non-UI thread and completes.
- [x] 2.3 Register `INotificationPresenter` -> `ToastPresenter` in `Program.cs` beside `SettingsEditor` and `SettingsWindowViewModel`, and call `AddNotifications()` there too. Close every open toast from `App.OnExit`, beside `_trayIcon?.Dispose()`, so one cannot outlive the dispatcher that owns it. Registering the two halves separately is the point: with `ValidateOnBuild` on, omitting the presenter is a startup failure naming `INotificationPresenter` rather than a null reference at the first error a user hits. Verify: a registration test resolving `INotificationService` and `INotificationPresenter` from a built host, in the manner of `SettingsWindowRegistrationTests`; and a manual quit with a toast on screen exits with code 0.

- [x] 3.2 Prove that nothing on the notification path can block the hotkey, with a test rather than by inspection. **The shape already exists one layer down**: `GlobalHotkeyServiceTests.SlowConsumer_DoesNotHoldTheHookThread` puts a slow consumer behind an edge and asserts the edge still arrives. ## 4. Autostart

- [x] 4.1 Add `Core/Autostart/`: `IAutostartService` with `bool IsEnabled()`, `void Enable()` and `void Disable()` — methods rather than a property, because all three do I/O — and `AutostartException`, mirroring `SystemShellException`. Add `AutostartReconciler`, an `IHostedService` that reconciles in `StartAsync` and on every `SettingsStore.Changed`: read `IsEnabled()`, compare to `Current.StartWithSystem`, write **only** on a mismatch, and log only when it writes. Reading before writing is the fix for a mistake already in the tree — `GlobalHotkeyService.OnSettingsChanged` logs `"Hotkey rebound to {Binding}."` outside `Rebind`'s early return, so changing the audio format writes a misleading line at the default level, and here the write would be a registry mutation rather than a no-op. Catch `AutostartException` and log it: a machine that refuses a Run value must not stop the application starting. Add `AddAutostart()`. Verify: unit tests over a fake `IAutostartService` and a fake store — enables when the setting is on and nothing is registered, disables when off and registered, **writes nothing when they already agree**, reconciles again on `Changed`, and survives a throwing service. `Unit` trait: no file, no container.
- [x] 4.2 Add `Platform/Autostart/WindowsAutostart`, `[SupportedOSPlatform("windows")]`, writing value `Pisum Whisper` under `HKCU\Software\Microsoft\Windows\CurrentVersion\Run` with the quoted `Environment.ProcessPath`. **The subkey path is injected**, defaulting to the real one — that is what makes this testable at all, and without it the only honest test writes to the user's real Run key and the capability is verified by hand for ever. **`Microsoft.Win32.Registry` needs no package reference**: verified in a scratch `net10.0` project with `TreatWarningsAsErrors`, the types resolve from the shared framework and the only diagnostics are three `CA1416`s, cleared by the platform attribute plus the `OperatingSystem.IsWindows()` guard in 4.4 — the same pattern `WindowsClipboard` already uses. Do **not** add anything to `Directory.Packages.props`. Verify: round-trip tests against a private `HKCU\Software\Pisum.Whisper.Tests\...` subkey deleted in `Dispose` — enable, `IsEnabled()` true, the value names the running executable, enable again and there is still one value, disable, `IsEnabled()` false. `Integration` trait, per 6.1.
- [x] 4.3 Add `Platform/Autostart/MacOsAutostart`, `[SupportedOSPlatform("macos")]`, writing `net.pisum.whisper.plist` into `~/Library/LaunchAgents` with `Label` `net.pisum.whisper`, `ProgramArguments` `[Environment.ProcessPath]` and `RunAtLoad` `true`, and deleting it to disable. **The directory is injected**, defaulting to the real one. No `launchctl`: `tauri-plugin-autostart`'s `MacosLauncher::LaunchAgent` writes the plist and nothing else, and `launchd` reads the directory at login. Verify: round-trip tests writing into a temp directory — these run **on any operating system**, so the plist's shape and the enable/disable/re-enable cycle are covered from Windows and only the effect on login needs hardware (7.2). Assert the written XML parses and carries all three keys.
- [x] 4.4 Add `AddNativeAutostart()` following `NativeOutputServiceCollectionExtensions` exactly — `OperatingSystem.IsWindows()`, then `IsMacOS()`, then `throw new PlatformNotSupportedException` naming `RuntimeInformation.OSDescription` — and call `AddAutostart()` and `AddNativeAutostart()` from `Program.cs`. ## Not in this change

Recorded so they are not mistaken for oversights, each with its owner:

- **`IShellService`.** The proposal asks for it; change 10 already shipped it as `Core/Shell/ISystemShell` and `Platform/Shell/SystemShell`, wired into the Logging tab. Nothing to do, and `design.md`'s drift table records it.
- **Respecting Do Not Disturb and Focus Assist.** A window this application draws is not suppressed by either, and nothing here mitigates it. It is the accepted cost of not depending on change 12, and it is in `design.md`'s *Risks* rather than left to be discovered.
- **Notification history.** Nothing this change shows persists anywhere after it is dismissed. A native transport would give it; S6 established that `Shell_NotifyIcon` would not have, so this is not a regression against the option that was rejected.
- **A native transport behind `INotificationPresenter`.** The interface exists so one can be added once change 12 registers an AUMID, and `spikes -- notify` stays in the tree because that is when its three unanswered observational questions matter again.
- **Rendering `HotkeyAvailability.Failed`.** Change 9 deferred the dead-hotkey case here on the grounds that this change brings a notification transport. It is genuinely adjacent, but it is a startup condition rather than a dictation failure, it has no title or message written for it, and the macOS grant it reports on is unverified on hardware — so it would widen this change past its proposal on top of behaviour nobody has observed. It needs its own proposal.
- **Packaging, the Start-menu shortcut and the AUMID.** Change 12. This change is written so that none of them are prerequisites.
